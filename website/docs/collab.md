# 会话协作

如果你同时开着几个 Agent 会话，可以让它们互相配合：一个负责前端、一个负责后端，中间不用你人肉传话。简单的委派使用会话协作；围绕同一个需求长期推进时，可以创建房间，由统筹管理成员与共享任务板。

:::note 版本说明
房间与共享任务板已在 v0.23 引入。下文标为「下一版本（Unreleased）」的持久化、投递阶段、待回复入口与历史浏览功能属于尚未发布的更新。
:::

## 稳定的会话名

为 Agent 会话设置一个**稳定名字**（比如 `前端`、`测试`），这个名字在项目内唯一，重开会话也保留。普通派活按侧栏的会话名寻找目标；房间消息按房间内的角色名寻找收件人。这些名字由你设置，不随界面语言改变。

> 在 Belfry 侧栏开好并命名了几条会话（reviewer、前端、测试这类），就是为协作指定了目标。说「交给前端」指的就是那条会话。

## 内置 belfry CLI

以下命令在 Belfry 管理的 Agent 终端中运行。先查看可用会话、加入的房间和命令帮助：

```sh
belfry peers
belfry rooms
belfry --help
```

示例中的会话名、角色名、任务号和消息编号都需要替换为实际值。加入多个房间时，在每条 `belfry room ...` 命令后加 `--room "房间名"`，明确操作哪一间房。

### 会话之间派活

派活方使用 `send`，并用返回的任务号查询或等待结果：

```sh
belfry send 测试 "运行登录流程的回归测试，并报告失败原因"
belfry wait <task-id> --timeout 60
```

接活方用 `inbox` 查看任务，结束后根据结果选择 `done` 或 `fail`：

```sh
belfry inbox
belfry done <task-id> "登录回归通过，验证记录已写入项目文档"
belfry fail <task-id> "测试环境无法启动，错误与复现步骤已记录"
```

`wait` 不加 `--timeout` 会持续等待；指定超时只限制这次等待，不会取消对方的任务，也不代表任务完成。这里的 `<task-id>` 来自 `send`，与房间任务板的 `T1` 等编号不同。

如果处理别人派来的任务时还要委派子任务，给 `send` 加 `--parent <task-id>`，以便追踪转派关系与层级限制。

任务按目标 Agent 排队。对方忙碌或正在等待确认时暂缓投递，回到空闲后依次提交。排队与实际提交的区别见下文「投递阶段」。

## 房间与共享任务板

从侧栏「协作房间」创建房间，为同一个需求选择统筹和成员，并填写目标、当前重点与约束。统筹拆解需求、分配任务、跟进进度；成员处理分配给自己的任务，并向统筹报告结果或阻塞。

进入房间后，可以查看对话、任务板、协作流程和成员终端。终端中的对应命令是：

```sh
belfry room status
belfry room log --count 20
belfry room brief
```

任务板使用 `T1`、`T2` 等房间内编号，区分待开工、进行中、已完成和归档，并可指定前置任务。统筹可以更新简报并派活，例如：

```sh
belfry room brief --objective "完成登录功能" --focus "先对齐接口" --constraint "保留现有登录方式"
belfry room task add "实现登录接口" --to 后端 --outcome "接口回归通过并写明调用方式"
belfry room task add "接入登录界面" --to 前端 --after T1 --outcome "登录与错误提示可用"
```

最后一行假设接口任务的实际编号是 `T1`；以命令返回的编号为准。成员接到任务后按进度更新：

```sh
belfry room task start T1
belfry room task note T1 "接口已完成，正在跑回归测试"
belfry room task done T1 "回归通过，调用方式已写入文档"
```

遇到阻塞时，用 `belfry room task note` 记录原因，并向统筹说明需要的帮助。统筹还可以用 `belfry room task assign T1 角色名` 调整负责人、`belfry room task reopen T1` 重新打开任务，或用 `belfry room task archive T1` 收起任务。归档只影响任务板，不会归档或删除房间历史。

房间任务用 `belfry room task done T1` 交差；普通委派任务使用 `belfry done`、`belfry fail`、`belfry wait` 和各自的任务号。

### 发送消息与暂停房间

```sh
belfry room say "接口已完成，调用方式见项目文档"
belfry room say "请确认登录接口参数" --to 后端 --ask
```

不写收件人时，成员的消息发给统筹，统筹的消息发给全体。用 `--to 角色名` 或正文中的 `@角色名` 指定收件人；`--to` 也接受 `@全体`、`@成员`、`@统筹`、`@用户`。下一版本（Unreleased）增加英文别名 `@all`、`@members`、`@coordinator`、`@user`。

暂停房间后，消息继续记录在房间里，停止向成员终端投递，空闲提醒也暂停；已经在执行的工作会继续。

## 待回复与按编号回复

发送消息时使用 `--ask` 会为收件人保留待回复事项。收到此类消息后，用它的消息编号明确回复：

```sh
belfry room say "参数已确认，可以开始接入" --reply <message-id>
```

`<message-id>` 是消息上显示的编号，不是任务板编号。带 `--reply` 的回复会解除相应收件人的待回复项；有多个收件人时，每人分别回复。成员可以用 `belfry room status` 检查轮到自己回复的事项，完成任务不等于回复了所有待回复消息。

**下一版本（Unreleased）**：房间提供「待回复与按编号回复」入口，可以打开原文、引用并回复。输入完整消息编号或无歧义的短编号即可定位；短编号有歧义时使用完整编号。早期待回复即使已离开最近 1000 条消息的窗口，重启后也仍然可查、可回复。

## 投递阶段（下一版本 / Unreleased）

协作面板将投递阶段与工作结果分开展示，并显示停留在该阶段的原因。房间对话也会显示发给各成员的消息是否排队或结果不确定。

| 阶段 | 含义 |
| --- | --- |
| 已受理 | 任务已保存，尚未进入目标终端的队列。 |
| 排队中 | 已进入队列，等待目标会话可以接收。 |
| 正在提交 | 开始提交，正在等待终端回执。 |
| 已提交到终端 | 终端已确认提交；仍需 Agent 报告工作结果。 |
| 提交结果不确定 | 可能已经写入终端，需要人工核对；不会自动重复粘贴。 |
| 投递已取消 | 已放弃本次投递；若此前结果不确定，仍可能已经写入终端。 |

`send` 成功表示已受理；排队不算已提交。「已提交到终端」也不表示 Agent 已开工或完成。普通任务由 `done` / `fail` 报告结果，房间任务由 `room task done` 完成任务板记录。

### 处理不确定的投递

普通协作任务显示「提交结果不确定」时：

1. 点击「去目标终端核对」，检查该条指令是否已经出现在终端中。目标会话不可用时，先恢复会话再核对。
2. 确认指令已经提交后，点击「确认已提交」；Agent 仍需继续完成任务并交差。
3. 如果决定不再投递，选择「放弃此任务」并确认。放弃不会撤回已经写入的指令，也不会停止已开始的工作。

核对期间若任务状态发生变化，面板会刷新；根据最新状态重新检查后再决定。房间消息出现不确定状态时，同样先检查成员终端再决定后续安排。

## 重启、历史与容量（下一版本 / Unreleased）

任务与待投递记录保存在本地，重启后任务号仍可查询。待投递任务恢复后继续遵守批准与排队规则，已提交任务不会自动重投；在提交中断时无法确认结果的任务会保留为不确定，等待核对。

房间主时间线保留最近 1000 条消息，可从顶部「加载更早历史」逐页浏览原文。待回复入口独立保留早期未完成事项，不需要先翻到对应历史页。分页中到达的新消息不会打乱当前阅读位置，未知或无法解析的历史记录会显示可读提示。

房间信息显示历史大小。**历史原文保留到删除房间；需要长期保存时，先备份应用数据目录。** 当前没有「归档旧历史」操作，手动删除账本会破坏房间数据，不能用它代替归档。

旧格式首次升级时需要迁移历史；之后启动从快照恢复当前状态与未完成事项，不再逐条读取全部历史。

## 批准闸门与协作面板

协作任务可以设置批准闸门：需要你确认的操作先经你点头再执行。循环与层级限制避免会话无限相互派活。协作面板可查看谁在等谁、待批准任务、投递阶段及 Agent 报告的完成或失败结果。

## 环境诊断

协作依赖 Belfry skill、CLI 登录态与协作通道。设置页提供诊断：

- Belfry skill 是否就位、是否为最新版
- 各 CLI 的登录、Provider 与功能状态
- doctor 结果与协作通道连通性

诊断可以自动同步或手动更新内置 skill。Codex、Claude Code、Pi、Antigravity CLI、OpenCode、Kimi Code 六种客户端分别报告状态，保留部分成功结果；例如 Claude 正常而 Codex 未登录时，仍可查看 Claude 的结果。
