## 设计与授权

用户在了解静态实现与上游的差距后明确要求“像这个开源项目一样的插件功能，帮我修改”。
据此实现 PI 清单适配、插件私有 IPC/类型、运行进程、插件设置存储和必要应用接线。
保留旧静态插件兼容；不恢复 Harness。当前分支直接实施，不委派、不提交或推送。
采用 brainstorming / writing-plans 的设计与拆分、executing-plans 执行、行为 TDD 和完成前验证。
既有源码分析及上述请求作为方向依据，不重复询问已经确定的插件模型。

架构：Rust 继续权威校验安装与注册表；应用启动受控 Node 宿主，每个插件在独立子进程
加载 `main.js`，宿主分发 `pi.*` API。脚手架、校验、打包复用 Node 作者工具。
Tauri 管插件窗口与系统交互，HTML 经插件专属访问令牌和受限桥接调用宿主。
终端 Agent 通过只对本机会话开放的 MCP 桥接使用插件工具与 Skill。

Node 从本机标准安装位置/PATH 发现，运行时源码随 Rust 编译嵌入；不在插件安装时下载依赖。
缺少 Node 时静态管理仍可用，动态运行和作者工具给出明确诊断。
插件进程不继承宿主凭证环境；进程隔离不宣称为 Node 原生能力的操作系统沙箱。

## 验收对象与边界

- PI 风格 `main`、`engines`、命令、Skill、设置、panel/view、Agent 工具及相关权限声明。
- 四种内置模板：`panel-basic`、`agent-tool-basic`、`skill-pack`、`full-demo`。
- 普通作者在 UI 创建目录，修改后重载，校验、导出 `.piplug`，另一实例安装并运行。
- 插件命令调用真实函数；设置可读写并重启保持；工具通过 MCP 被 Agent 发现和调用。
- HTML 面板使用 `window.pluginBridge`；禁用、卸载、失败及应用退出均清理进程和贡献。
- 在基础流程后接入服务、主题、消息总线和声明式 MCP；宿主专属 API 明确说明可用范围。
- 现有 Shell、Agent、协作与静态插件回归；不覆盖其他工作区改动。

## 文件分工

| 范围 | 责任 |
| --- | --- |
| `src-tauri/src/plugins/pi_*.rs` | PI 清单解码、资源与权限校验、旧清单适配 |
| `src-tauri/src/plugins/engine/` | Node 宿主、消息边界、退出、窗口与 IPC |
| `src-tauri/src/plugins/node/` | 作者工具、每插件进程、宿主 API、面板服务与 MCP |
| `src/plugins/` | 创建、校验、导出、命令运行、设置编辑、工具和运行状态 |
| 应用/Quick Open/Agent 入口 | 上下文、命令入口、MCP 参数与退出接线 |
| `examples/plugins/` | 可安装、可执行的样例与作者文档 |

新模块每文件不超过 300 行，函数不超过 50 行；按输入边界和职责拆分。
不引入新 npm/Cargo 依赖；根构建配置沿用现有入口。
