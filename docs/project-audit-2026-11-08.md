当前产品已经形成完整的本地 CLI Agent 工作台：终端与后台恢复、项目与命名工作区、Provider、协作房间、插件、Git Diff/Worktree、历史和用量统计都已实现。下一轮应先修好协作流程的可靠性，再把任务交付、历史追溯和环境诊断做完整。

README 的已交付路线图止于 v0.17，不能直接当作当前待开发列表。Git 集成、费用估算、后台恢复等已有能力应在现有模块上扩展，避免重复开发。`docs/design/fun-feature/technical-assessment.md` 引用的是更早的房间模型，其中 `Verified`、`roomVerifyTask` 等接口不属于本次基线。

## 优化项与优先级

P1 表示建议下一轮先修；P2 表示修复主流程后安排。没有把尚未量化的性能推测列为已复现缺陷。

### P1：协作 CLI、应用与常驻后台的兼容性

本轮按要求创建房间任务失败，两位成员改用 `belfry send` 接到审查任务。直接使用仓库内已构建 CLI 运行 `room status` 也失败，因此不能仅归因于 PATH 中选错 CLI。

后端现场核对：已安装 GUI/CLI 为 v0.23.0，但当前协作 TCP relay 的监听后台启动于 11 月 7 日 13:28，早于房间协议重写提交 `535a612`（当日 23:20）。`client.rs:303` 在 Ping 成功时继续复用旧后台；单独升级 CLI、重开 GUI 或新建会话不会替换它。`rooms/status/task` 没有可绕过旧命令类型解析的参数写法。

本次基线已经把后台转发的**请求**改成读取 JSON 信封；**响应**仍反序列化为固定 `Response`/`ResponseData`，新响应类型或字段仍可能被旧后台拒绝。旧版本 `RoomSaid` 不包含当前的 `message` / `ask` 字段，经过反序列化和重新序列化还会丢掉这些新字段。因此，CLI 报解析失败不能直接推断业务动作未执行，重试前应查回执并避免重复写入。

汇总时工作区已出现其他会话的双向透明转发修复及对应回归改动。这一项的下一步应先验收现有改动、旧后台处理方案与真实房间链路。本轮未替该并行改动执行最终验收，也未将源码修改视为当前常驻旧后台已更新。

- 代码入口：`src-tauri/src/terminal/daemon/relay_collab.rs:26`、`:48`；`src-tauri/crates/belfry-protocol/src/lib.rs:169`。
- 诊断缺口：`src-tauri/src/setup/diagnostics.rs:62` 只用 `peers` 检查连通，无法说明房间命令可用。
- 开发建议：对请求和响应均按边界转发、明确能力与版本诊断；覆盖旧后台常驻、新应用启动、CLI 更新的组合。恢复方案应保留现有 PTY，不以结束全部后台任务为默认修复。
- 验收：同一会话完成 `peers → rooms → status → task add/start/done → say/reply`；旧版组合返回明确的不支持原因；未来响应能够穿过中继；任务不重复投递，原 PTY 保留。
- 负责人：后端主导，前端补充可操作的诊断反馈。规模：中。

### P1：投递事实与应用重启后的任务恢复

`useTaskDelivery` 在 Prompt 队列返回 `queued` 时也标为 `Dispatched`，房间 reconciliation 随即记录“进过成员终端”并移除总线记录。目标之后仍可能关闭或投递被取消，此时页面的“已送达”与实际输入不一致。同时 `TaskBoard` 仅在内存，原先“会话跨不过应用重启”的前提已被后台 PTY 功能改变：Agent 还活着，重开的应用却可能不再认识原任务编号。

- 代码入口：`src/collab/useTaskDelivery.ts:12`、`:39`；`src/prompt/runtime.ts:74`；`src-tauri/src/rooms/store.rs:364`；`src-tauri/src/collab/task.rs:319`。
- 开发建议：持久化任务和待投递记录；区分受理、排队、实际提交、结果不确定及完成。复用 Prompt 队列已有 observer 的 `submitted` 回执，关联稳定的消息/任务 ID。
- 验收：目标忙时不显示已进 PTY；在入队、写入、回执各阶段重启应用，任务编号仍可查询，确认提交的内容不重复投递，取消与不确定状态可见。
- 负责人：前后端联调。规模：大；这是诊断与恢复中心的基础。

### P1：房间切换与轮询的迟到响应

`useRooms.refresh()` 在 `roomGet(current)` 返回后直接写入房间，没有重新核对当前选择或请求代次。已用当前源码复现：选择 A、让 A 请求延迟，切换 B 并拿到 B，再释放 A 请求，结果 `selectedId=B`、`room.id=A`。同一房间的旧轮询也可能覆盖刚完成的操作。

- 代码入口：`src/rooms/useRooms.ts:65`、`:76`、`:91`、`:98`。
- 开发建议：为刷新建立请求代次及选择校验，操作完成时使旧快照失效；轮询避免重叠，并在卸载时停止应用迟到结果。
- 验收：A/B 乱序、连续轮询乱序、删除/切换后迟到响应、操作成功后旧轮询返回，都不能改变当前房间或回滚显示状态。
- 负责人：前端。规模：小。

### P1：待回复事项不能依赖最近 1000 条消息

房间投影超过 1000 条会移除最早的消息，而待回复列表和按编号回复都仅查这份投影。因此，未回复请求可能随聊天增长消失。账本超过 3000 个事件时，启动压缩会用当前投影重写文件，更早记录也会被移除。这里需要同时解决活跃事项保存和历史保留策略。

- 代码入口：`src-tauri/src/rooms/model.rs:16`、`:278`；`src-tauri/src/rooms/ledger.rs:149`、`:255`；`src-tauri/src/rooms/directory.rs:124`；`src-tauri/src/rooms/store.rs:445`。
- 现有回归 `src-tauri/src/rooms/rooms_test.rs:445` 验证了压缩后的投影一致，但未要求最早的未回复请求仍可处理。
- 开发建议：独立保存未完成回复/未送达事项；历史分页或分段归档；明确保留期限，压缩不移除仍被引用的事项。
- 兼容性也需保护：未知账本版本/kind 或中间损坏行当前会被忽略，随后按投影压缩可能永久移除这部分原始数据；不能把未知内容当作可安全删除的历史。
- 验收：超过 1000 条消息、超过 3000 个事件并重启后，早期未回复事项仍在、仍能回复，附件和引用可以追溯；保留策略有用户可见说明。
- 负责人：后端主导，前端负责历史与待办入口。规模：中。

### P1：房间提交与恢复的一致性

`persist()` 先同步追加账本，再替换 `rooms.json`。第二步失败时内存仍是旧状态，但账本已写入“新增任务/成员”等通知，重启后可能出现通知与任务状态不一致。重试会生成新事件 ID，按事件 ID 的幂等不能等价于业务操作幂等。

- 代码入口：`src-tauri/src/rooms/store.rs:410`、`:417`、`:427`；`src-tauri/src/rooms/ledger.rs:233`。
- 开发建议：统一事务边界或带 commit marker 的日志；故障恢复只接受完整旧状态或完整新状态。通用原子写入还应区分 rename 可见性与断电耐久性，并评估同一数据目录的多进程单写者约束。
- 验收：对 append、sync、rename 注入故障；重试和重启后不出现未成功操作的通知，不丢任务、不重复记录。多实例修改不能用旧快照覆盖新数据。
- 负责人：后端。规模：中。磁盘故障、断电与多进程覆盖目前是源码确认的风险，未在真实用户存储上实验。

### P1：插件设置容量与超时收尾

后端使用临时目录复现：设置单次写入限制 64 KiB，但合并后的总文件不限；18 次各约 60,000 字符写入成功后，文件达到 1,080,262 字节，超过读取的 1 MiB 上限，后续读写都报错，插件重新加载也会受影响。

- 代码入口：`src-tauri/src/plugins/node/settings.mjs:16`、`:30`、`:35`、`:38`。
- 修复与验收：写入前检查最终序列化字节数；超限保留原文件；覆盖累计增长、中文、默认值和并发合并，并提供旧超额文件的导出/修复入口。规模：小。

后端另用隔离进程复现：插件调用报 TIMEOUT 后，忽略 SIGTERM 的子进程仍存活。Rust 宿主的响应超时位于阻塞写管道之后，满管道时也不能保证按时结束。

- 代码入口：`src-tauri/src/plugins/node/child.mjs:68`；`src-tauri/src/plugins/engine/connection.rs:124`、`:152`、`:173`。
- 修复与验收：截止时间覆盖排队、写入和等待；TERM 宽限后强制结束并回收；覆盖满管道、忽略 TERM、子孙进程和取消无响应，同时其他插件能继续调用。规模：中。

### P1：CLI 等待必须有真正的截止时间

`wait --timeout` 在 `send()` 返回后才检查时限，但 socket 没有读写超时。后端假服务接收请求后不回包，实测 `wait --timeout 1` 超过两秒仍阻塞。CLI 读取响应也没有帧长度限制。

- 代码入口：`src-tauri/crates/belfry-cli/src/main.rs:76`、`:407`、`:420`、`:427`；服务端连接边界见 `src-tauri/src/collab/server.rs:155`、`:206`。
- 修复与验收：IPC 独立 deadline、响应长度上限、服务端读超时与连接预算；无回包、半行和超长回包均有界返回，超时仍明确表示未完成。
- 负责人：后端。规模：中。

### P2：房间规模与启动性能

主入口体积较大，但体积本身不能证明启动慢。房间已经有懒加载、消息 memo 和结构共享；仍每 1.5 秒拉取整间房，时间线遍历全部消息。应先测量再按数据拆分。

- 代码入口：`src/rooms/useRooms.ts:7`、`:15`；`src/rooms/view/RoomView.tsx:799`；`src/components/lazy/`；`vite.config.ts`。
- 开发建议：记录桌面冷启动、首个终端可输入时间、多会话输入延迟和大房间滚动数据；合并重复轮询，按房间 revision/事件增量更新；需要时做历史分页与虚拟列表，再调整入口依赖。
- 后端同时控制任务/结果字段总量与分页：当前 `room status` 返回所有未归档任务，数据增长后可能超过 relay 1 MiB 响应上限；账本启动时也会整文件读取。
- 验收：固定机器和夹具比较优化前后；终端不因切换面板重挂，输入、滚动定位、未读分隔线和消息引用无回归。
- 负责人：前端主导，后端提供增量数据。规模：中。
