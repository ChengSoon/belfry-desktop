# 平行宇宙挑战场：功能提案与开发计划

日期：2026-10-30。负责人：项目经理。状态：方案评审；尚未实现。

## 1. 推荐方向

把一个真实开发需求变成一场有作品的创意挑战：选择两张玩法卡，让两个 Agent 在各自的 Git worktree 中做出不同版本，比较作品、选择喜欢的版本、收藏配方，再发起下一轮。

例子：用户输入「做一个番茄钟」，A 路选择「街机游戏感」，B 路选择「安静的纸质手帐」。双方都必须支持开始、暂停、重置和键盘操作。完成后，用户看两版成果及验证记录，选择 B，并在下一轮给 B 加上「离线优先」卡。每轮留下真实代码、变更证据和可复用配方。

可玩性来自用户能决定风格、约束和下一轮方向，且每次都得到不同作品。卡牌组合提供变化，收藏提供积累，再次挑战提供连续目标。两路使用不同卡牌时，这是创意探索，不能据此给模型能力排名。

## 2. GitHub 调研

通过 GitHub 仓库搜索 API 检索 `pixel-agents`、`ai town`、`agent worktree arena` 等关键词，并读取下列 README。检索日期为 2026-10-30；未安装、运行或审计这些项目，以下是文档层面的参考。

| 项目 | 已核对的机制 | 对 Belfry 的借鉴与边界 |
| --- | --- | --- |
| [Pixel Agents](https://github.com/pixel-agents-hq/pixel-agents) | 将终端 Agent 映射为像素角色；状态动画、办公室布置；README 将更多游戏机制列为后续方向 | 借鉴状态可视化与轻量反馈。API 标识代码为 MIT，README 提到第三方角色素材，素材许可需另核对 |
| [AI Town](https://github.com/a16z-infra/ai-town) | 可定制 AI 角色、小镇和模拟状态；Convex 与 PixiJS 架构 | 借鉴角色参与感。完整世界模拟和额外模型调用超出本次 MVP；API 标识代码为 MIT |
| [Agent Arena](https://github.com/orangejustin/agent-arena) | 相同任务、CLI Agent、平行 worktree、diff 比较、选择结果 | 证明该工作流已有公开实现可供研究；API 未返回许可证，不直接复制代码 |
| [bon-arena](https://github.com/jacksuzuki/bon-arena) | 独立 worktree、收集 diff/test/lint/typecheck、比较、选择与采用分开 | 借鉴结果证据和分阶段操作；API 标识 MIT，集成前仍需核对具体文件和依赖 |

判断：并行竞赛本身已有先例。Belfry 的产品差异应落在「玩法卡 + 可比较作品 + 连续挑战 + 原生终端接管」，而非宣称首创。首版自行实现业务层，不引入这些仓库的运行时或美术资产。

候选取舍：像素办公室适合观赏与布置；完整 AI 小镇内容空间大，但引入额外模拟系统；挑战场最贴合 Belfry 现有终端、协作任务与 worktree，优先验证这一方向。此判断是产品取舍，尚无用户实验数据。

## 3. 首版体验

1. 从项目工具区或协作房间进入「挑战场」，输入需求和共同验收项。提供番茄钟、目录搜索、README 改版三个示例。
2. 每路选择 Agent 配置与一张可编辑玩法卡；可随机抽卡、重抽，也可手选。展示最终发给双方的完整要求，卡片只是可见的提示词约束。
3. 展示两个新分支、共同基础提交及专用会话的创建计划。用户点「开始挑战」后先创建两个目录，核对均 ready 且 `baseHead` 相同，再启动会话；不迁移用户已有会话的工作目录。允许同一种 Agent 配置开两路。
4. 双栏展示 A/B 的排队、投递、等待输入、交差状态。点击一侧即可进入其真实终端。权限问题继续在原终端处理。
5. 每路在自己的候选分支提交作品并交差后，收集相对共同基线的变更和验证记录。两个有效成果都封存后进入正常比较；一侧失败时提供保留单侧成果的明确分支。允许「都喜欢」「都不满意」。未提交的工作会展示待补交及差异，不当作已封存成果。
6. 用户收藏作品/配方或选定版本；「查看合并预览」是独立操作。再次挑战复制需求和卡牌，重新选择基线；使用获胜代码作为基线前必须先有明确的提交。

建议的首套六张卡：极简交互、街机风格、纸质手帐、键盘优先、离线优先、零新增依赖。前 3 张适用于 UI；后 3 张按项目能力标注适用范围。卡片冲突必须在开始前可见并允许编辑，不静默拼接互相矛盾的要求。

「隐藏作者」只隐藏比较页的 Agent 标签。用户看过运行终端或代码后可能知道作者，因此不声称严格盲测。共同验收项、卡牌差异和验证来源始终可见。

## 4. UI 设计约束

- 沿用 Belfry 的主题、字体、按钮、对话框和双栏布局，新增卡牌纹理与少量抽卡/揭晓动效；支持减少动态效果。
- 页面顺序：需求与卡牌设置、双路进展、作品比较、收藏记录。窄窗口将双栏改为 A/B 切换，键盘能完成抽卡、选择、切换、打开终端。
- 首版创建流程限定主窗口；独立房间窗口目前不能创建成员会话，从该窗口进入时定位到主窗口挑战页。比较页的 A/B 展示顺序随机一次并持久化，刷新后不交换作品与选择结果。
- 运行页只展示可核实状态，不画虚构的完成百分比。动画不能把「正在输出」解释为「正在写代码」或「测试通过」。
- 第一版比较内容为需求满足情况、文件变化、受限文本 diff、Agent 提交说明与验证证据；继续用现有终端启动/查看作品。自动启动网页服务器、内嵌任意应用和截图采集放后续。
- 耗时与已有可归属的用量可展示；拿不到的数据写「暂无数据」。不虚构费用，不用计时器冒充硬 token 预算。

## 5. 范围

| MVP 必须有 | 后续扩展 |
| --- | --- |
| 一轮、两路、同一基础提交；允许相同 Agent 配置 | 多路淘汰赛、合作接力 |
| 六张内置卡、手动编辑、记录抽卡种子及卡片版本 | 卡组导入导出、主题包 |
| 专用会话、独立目录、明确交差与失败状态 | 像素角色观战、时间线回放 |
| 逐路成果证据、人工选择、收藏、再次挑战入口 | 自动预览与截图、可配置验证执行器 |
| 部分失败、重启对账、幂等防重复、显式合并预览 | 自动评委、融合两个版本 |

首版面向有提交历史的本地 Git 项目。只从明确的已提交内容开始，未提交修改不自动复制。SSH、无 Git 项目、共享在线榜单和后台无限比赛不在首版范围。

## 6. 实现落点

新增建议目录为 `src/arena/` 和 `src-tauri/src/arena/`，名称及接口在技术评审后冻结。先做宿主内置能力：本功能需要协调终端生命周期、协作投递和 worktree，当前不假定插件已暴露这些能力。

| 现有能力 | 代码位置 | 使用方式与缺口 |
| --- | --- | --- |
| Worktree 创建、操作预览及执行 | `src/git/worktrees/api.ts`、`src-tauri/src/git/worktrees/service.rs` | 复用预览/执行和操作校验；新增双候选编排，固定同一 `baseHead`，记录部分成功，禁止第二路失败后重复创建第一路 |
| 房间、成员、任务与项目范围 | `src/rooms/api.ts`、`src-tauri/src/rooms/commands.rs` | 复用成员绑定和任务来源；两张卡必须生成独立任务文本，并将两路目录纳入明确范围 |
| 指定目录创建成员会话 | `src/App.tsx` 的 `launchRoomMember` | 已支持按目录启动协作模式会话；从主窗口调用，保存 candidate/tab/member 映射 |
| Agent 投递和交差 | `src/collab/useTaskDelivery.ts`、`src-tauri/src/collab/` | 复用队列、`done/fail` 与任务 ID；空闲/屏幕安静不是完成信号 |
| 持久化基础 | `src-tauri/src/atomic.rs`、`src-tauri/src/collab/task.rs` | 可参考原子替换写法，但 TaskBoard 目前仅在内存；挑战必须新增可靠存档、投递意图、交差持久化及启动恢复，不能直接宣称可跨重启恢复 |
| 房间任务产物 | `src/rooms/contracts.ts` 的 `TaskArtifact`、Rust 的 `capture_artifact` | 现有房间级证据不能直接当双路证据；必须按候选目录、attempt 与冻结提交分别采集 |
| 差异查看与人工合并 | `src/git/GitDiffView.tsx`、`src/git/worktrees/` | 复用展示和合并预览；选定作品不等于合并成功，不默认清理落选目录 |

worktree 隔离的是工作目录与分支，不是操作系统沙箱。专用 Agent 仍遵守现有权限模型；不能向用户承诺进程或文件访问的强隔离。

### 建议数据契约

- `ChallengeRun`：id、schemaVersion、repoKey/commonDir、projectRoot、baseHead、brief、acceptance、seed、cardSnapshots、displayOrder、revealedAt、createdAt、revision、stage、selectedCandidateId/artifactId。
- `CandidateAttempt`：candidateId、runId、slot、attempt、worktreeId/path、tabId、daemon/nativeSessionId、busTaskId、最终 prompt 及 hash、交差状态、证据状态、artifactId。重试追加 attempt，保留旧记录。
- `Artifact`：candidateId、attempt、capturedAt、baseHead、resultHead、文件清单及 hash、受限 diff/截断标记、提交说明、验证记录。正式成果按不可变 commit OID 封存，完整比较 `baseHead -> resultHead`，包含新增文件；额外读取当前已暂存、未暂存和未跟踪差异，提示未提交内容并阻止误封存。
- `Verification`：命令、cwd、时间、退出码、结果来源。Agent 自报与宿主观察明确区分；没有执行证据时标「未验证」，首版不引入独立自动执行器。
- `CollectionEntry`：runId、candidateId、用户备注、配方快照。收藏幂等，不依赖会话仍在线。
- `Event` 与待投递意图：eventId、runId、seq/revision、candidateId/attempt、actor、type、at、payload。创建、投递、交差、封存、取消、恢复、选择与揭晓均留痕，与状态在同一次存档中更新。

建议新增命令覆盖计划预览、创建、读取、重试失败路、停止派发、选择与收藏；具体 IPC 签名由前后端共同冻结。不能给前端一个绕过 worktree 预览校验的「强制采用」接口。

### 生命周期与恢复

挑战状态建议为 `draft -> preparing -> active -> reviewable -> selected/archived`，另有 `interrupted`。候选状态至少区分创建、排队、已投递、已交差、证据失败、任务失败、中断；等待输入是会话活动状态，不冒充任务终态。

- 创建前保存运行意图；每个有副作用的步骤写入候选 ID 和操作结果。持久化失败不得继续投递或确认交差。锁、revision 和 requestId 防双窗口竞争与重复操作；关键确认补同步写盘。重试只处理失败/未执行步骤。
- 两路都从相同 SHA 创建；准备过程中基础分支变化时中止或要求重新预览，不能让两路悄悄使用不同代码。
- `done` 只触发收集，匹配 `busTaskId + attempt` 并核验不可变成果后才算提交。重复或迟到回执不能覆盖新一轮，也不能重复收藏。当前 TaskBoard 可让 Abandoned 被迟到 done 改写，挑战自己的取消终态必须在持久化事务中裁定。
- `done` 后采集作品前核对该会话是否仍在写入；无法稳定采集时标记待采集，不能把变化中的目录宣称为冻结成果。再编辑后必须重新采集。
- 重启后先对账任务、会话和目录，再更新状态；不自动重放已投递任务。TaskBoard/PromptQueue 重启会丢失，但 daemon 会话可能仍活着：恢复原 taskId 与原会话绑定，或创建显式恢复 attempt；不确定是否送达时标中断，不盲目重投。新旧 attempt 不得并发写同一目录。
- 普通 `send` 按项目根字符串判同项目，不能直接投到另一个 worktree。挑战投递应核验 canonical Git commonDir 和本次两个已授权目录，不全局放开跨项目。`Dispatched` 仅表示前端队列已接管，不能用它宣称 Agent 已执行。
- 「停止派发」不等于已停止 Agent 进程。首版分别展示取消排队、已请求中断、已确认停止；只有终端生命周期证据能确认执行结束。
- 当前比较结果过期或目标分支发生变化时，采用流程重新生成预览。冲突保留现场；清理作为单独操作。
- 现有 worktree 清理要求已合并、无未跟踪/忽略文件且无运行会话；通常不能清理落选分支。首版明确保留目录，不能承诺「自动收拾残局」，也不借机放宽现有清理保护。

## 7. 开发分工与排期

已通过 belfry 向真实会话派出只读可行性调研：前端开发任务 `3r9jsx7e`、后端开发任务 `vmhwmdxb` 均已用 `done` 交差，结论已纳入本文。这两项是调研，不代表生产实现已启动。

| 阶段 | 负责人 | 交付与退出条件 |
| --- | --- | --- |
| M0：范围与接口 | 项目经理 + 前端开发 + 后端开发 | 收敛创建/投递/采集/取消契约；确认双 worktree、双会话最短闭环与协议兼容问题；给出修订估时 |
| M1：双路闭环 | 后端开发主责，前端开发接线 | 同一 SHA 创建两路，记录任务 ID；各自交差，能按路读取成果；其中一路失败可恢复 |
| M2：可玩交互 | 前端开发主责，项目经理验收 | 玩法卡、运行视图、比较、选择、收藏、再次挑战；先用固定 fixture 开发，再接真实 API |
| M3：可靠性与交付 | 前后端共同负责，项目经理统筹 | 重启/迟到回执/部分失败/合并冲突回归；macOS 与 Windows 原生冒烟；保留普通终端工作流 |

综合估计：前端 5-7 人日，后端 8-12 人日，合计约 13-19 人日；两人并行约 2-3 周，M0 后再确认接口接线与平台联调余量。此前 7-10 个工作日的粗估已因 TaskBoard 非持久化、投递恢复和逐路成果封存的缺口上调。后端估计以目录和会话绑定明确为前提；前端已找到现有按目录启动新会话的入口，本方案采用新会话，不包含运行中会话的迁移。协议兼容修复单独列依赖，未估工时，不承诺包含在上述窗口中。

建议节奏：第 1 周完成 M0 和 M1 的正常双路闭环，同时做卡牌/比较界面；第 2 周补成果封存、异常恢复与真实联调；第 3 周作为跨平台验证和缺口修复的规划余量。只有通过 M0 才冻结具体交付日期。

建议文件责任边界：前端开发负责新增 `src/arena/` 与入口接线，后端开发负责新增 Rust 模块及注册；共享 TypeScript/Rust 契约在 M0 一次对齐，避免同时编辑相同文件。项目经理维护本文、卡片内容和验收记录。

## 8. 验收与成败判断

功能验收必须覆盖以下场景：

1. 两个候选的 `baseHead` 相同、目录不同，提示词除明确卡片差异外共享同一需求与验收项；原工作区内容不受创建流程改动。
2. 一路等待权限或失败时，另一路能继续；界面如实展示原因，不能自动替用户确认。
3. 同时产生已提交、未提交、新增及二进制文件时，证据归属正确且截断可见；只自报测试成功时不显示宿主验证通过。
4. 第二个目录创建失败、重复点击开始、应用重启、重复/迟到 `done` 均不产生重复会话、重复任务或假成功。
5. 取消排队与中断运行状态可区分；落选作品保留；选择、提交、合并、清理按各自实际结果展示。
6. 合并前代码变化导致旧预览失效；发生冲突保留两个候选与目标分支现场。
7. 在 macOS/Windows 分别完成一次真实双路流程；窄窗口、键盘操作和减少动态效果可用。

实现后运行有针对性的状态机、恢复和路由单测，再执行仓库要求的前端测试/构建与 Rust 检查。当前只有方案文档，不把未运行的检查写成通过。

首轮产品试用建议邀请 5 位现有用户，每人完成至少一轮，记录是否能独立开始、是否理解卡牌差异、是否愿意再次挑战，以及最终是否保留一个真实成果。此为待执行的验证计划，不预先宣称留存收益。

## 9. 本次环境观察

`belfry peers` 与 `belfry send` 可用；`belfry rooms`、`belfry room log`、`belfry room say` 均返回「协作请求格式无效」。后端开发确认当前 endpoint 的监听进程为 10 月 24 日启动的旧 daemon，而 CLI/应用文件在 10 月 30 日更新。旧协议不含房间命令，但协议版本未变化，客户端 Ping 成功后继续复用旧 daemon。

`src-tauri/src/terminal/daemon/relay_collab.rs` 在转发前按编译时 Request 枚举解析整个请求，未知房间命令在这里被拒绝。长期修复建议：握手提供能力/构建信息，中继在验证 envelope 后透明转发 command 与 response payload，并补新 CLI/旧 daemon 的兼容回归。临时恢复需要在保存所有会话现场后结束旧后台 daemon 再启动最新版，单纯重开 UI 不够。

本次未停止任何会话、未修改运行时数据。群聊发送已实际尝试但失败，不能记作已发布；本文及前后端完成回执是当前交付物。
