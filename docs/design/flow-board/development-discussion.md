# 流程功能开发 · 设计侧提案

日期：2026-10-30。依据：本目录 `design-spec.md` 与当前仓库源码。用户原先发来的剪贴板文件为 0 字节，暂按房间名称及现有设计稿，把讨论对象理解为「任务节点 + 依赖连线」的干活看板。

本文是设计侧的待讨论提案，不代表开发成员已经认可。当前 `belfry peers` 可用，`rooms`、`room log` 与此前的 `room say` 返回「协作请求格式无效」；向「开发」发送讨论请求时，对方处于 talking，命令拒绝接收。

## 首版建议

把看板作为协作房间的一个视图。用户在同一间房里画任务、指定负责人、连依赖；点「派活」后复用房间任务、真实终端与交差回执。

先跑通一个可验证的例子：设计 → 开发 → 验证。设计交差后显示「待验证」，用户验收后开发节点才可派；开发失败时，验证节点继续等待，其他没有依赖开发的分支仍可使用。

首版包括：节点与依赖编辑、选择房间成员、保存画布、手动派活、查看交差与验收、失败后重试、打开对应终端。运行时可移动节点、查看详情；改变任务内容、负责人或依赖必须创建新版本，已经派出的任务保留当时的内容与关联。

「整条流程自动推进」、条件分支、循环、自动创建会话、跨房间流程、自动隔离 worktree 放在后续阶段。当前设计稿的「不引入中央调度器」与「跑整条流程」需要统一：首版按用户操作推进；后续自动推进可以是按已画依赖执行的确定性规则，但需要另外定义启动、暂停、恢复和并发上限。

## 交互与状态

节点只承担一件事、一个负责人。卡片显示任务名、负责人、状态及阻塞原因；详情显示任务内容、验收条件、前置产物、交差记录和「打开会话」。缩略画布上不堆转录全文与统计项。

| 节点显示 | 依据 | 主要操作 |
| --- | --- | --- |
| 等待前置 | 至少一个前置节点尚未验收通过 | 查看具体前置 |
| 可派活 | 无前置，或所有前置已验收；尚无当前执行尝试 | 派活 |
| 排队中 | 当前投递为 queued | 查看接收者、取消排队 |
| 已送出，等待交差 | 当前投递为 dispatched | 打开终端 |
| 已提交待验证 | 接收者通过 `belfry done` 交差 | 查看产物、验证通过、退回 |
| 已完成 | 用户验收通过 | 查看验收记录 |
| 失败 | 接收者通过 `belfry fail` 说明失败 | 查看原因、重新派发 |
| 已停止跟进 | 用户停止这条任务的后续处理 | 查看最后记录 |
| 结果未知 | 原投递记录找不到，无法确认执行结果 | 查看终端、决定是否重派 |

依赖是否满足、任务投递状态、会话能否接活是三个不同事实。成员忙碌、等待选择或已经退出时，显示对应原因；不能因为「依赖满足」就宣称现在一定能投递。

现有总线没有「已经开始执行」回执，因此 dispatched 不应直接显示为「正在执行」。取消排队也不能当作中断终端执行；已送出的任务要说明「后续已停止，终端可能仍在执行」。需要中断时引导用户打开对应终端，不能仅改画布状态来模拟暂停。

首版统一人工验收再开放后继节点。原型的 `auto / confirm / readonly` 不直接成为生产权限开关；「只读评审」如果只有提示词约束，就只能作为任务用途说明，不能承诺工具与文件系统只读。

## 与现有实现的接法

| 能力 | 已核对的代码 | 落地建议 |
| --- | --- | --- |
| 房间、成员、任务与历史 | `src/rooms/contracts.ts`、`src-tauri/src/rooms/store.rs` | 流程归属房间；复用成员与任务记录 |
| 派活、验收、退回、重派 | `src/rooms/api.ts`、`src-tauri/src/rooms/commands.rs` | 在 Rust 业务层抽取共用操作，图视图和房间视图读取同一份任务事实 |
| 接收者与交差身份 | `src-tauri/src/collab/task.rs` | 交差按总线任务 id 与实际接收者校验 |
| 会话可接活状态 | `src/collab/contracts.ts` | 当前实现只允许 idle 接收；首版如实显示，忙时自动排队需要单独改造 |
| 统计 | `src/usage/session/contracts.ts` | 当前统计属于会话；未建立节点尝试的计量边界前标注「会话累计」，缺失显示暂无数据 |

新增图数据建议只包括 `flowId`、`roomId`、版本号、节点和依赖；节点保存稳定 `nodeId`、`memberId`、任务内容、验收条件与位置。角色名可以修改，用来展示；执行时记录当时的 `tabId`，避免角色改名或换会话后错误归属历史。

把画布定义和执行记录分开。每次运行固定图版本，每个节点的每次尝试记录 `runId / nodeId / attemptId / roomTaskId`，同时保留实际投递与前置产物引用。新一次重派不覆盖上次记录；迟到的交差只能归入它原来的尝试，不能把新尝试直接标成完成。

沿用现有设计稿的约束：同一种 Agent 可以在多个节点使用，各节点绑定独立的真实会话；首版选择用户已经创建的会话。同一会话同时只接一个流程节点。并行会话若共用同一工作目录，仍可能互相覆盖修改，不能将「不同会话」描述成文件隔离。

## 实现前需要修正的设计稿假设

1. **房间任务已落盘。** `RoomStore` 使用版本化 JSON 和原子替换；内存态的是 `TaskBoard` 投递表。新增图存储并不能自动解决重启恢复，必须同时处理图与房间任务关联，以及投递记录丢失后的「结果未知」。
2. **图成环检测需要单独实现。** 现有 `task.rs` 的 `path / hop` 检测防止 Agent 转包绕回及层数超限；它没有检查整张流程图。图编辑和派发前都要校验依赖 DAG，后端为最终裁决方。
3. **派发需要幂等与一致的保存顺序。** 现有 `room_dispatch` 没有外部幂等键。流程派发应在后端完成前置校验、记录尝试与关联、生成投递；至少保证重复点击只创建一次。图和任务之间若分文件保存，需要可恢复的关联记录；不能依赖前端先派任务、再补存节点。
4. **产物不是天然的节点专属 diff。** 当前 `TaskArtifact` 采集的是房间项目工作区快照。共用目录时只能如实标明范围；向下游传递已验收的交差结果及明确引用，不把整个工作区的变化都归给某一节点。

## 开发顺序与验收

1. **契约与状态闭环。** 开发侧确定流程/运行/尝试的存储方式，设计侧对齐状态、按钮和错误文案；先用普通列表验证派发 → 交差 → 验收 → 后继可派。
2. **接入画布。** 节点/连线编辑、详情面板、依赖提示、键盘操作；接入同一套后端状态，房间与画布切换后结果一致。
3. **补恢复与真实联调。** 覆盖重启、重复派发、迟到回执、角色改名、换会话、退回重派；在 macOS/Windows 的真实终端验证成功链路和失败恢复。

首版通过标准：前置未验收不能派后继；重复点击只投递一次；重派后旧回执不污染新尝试；重启不自动重复执行；已送出不会冒充已开工；图和房间显示相同交差/验收事实；禁止成环；键盘可以完成选择节点、查看依赖、派活与验收。

待与「开发」对齐的三个决策：看板是否直接归属现有房间；运行记录是否与房间任务同处一个事务边界；首版是否接受人工推进与验收。以上为建议范围，本轮未修改生产代码、未执行运行测试。
