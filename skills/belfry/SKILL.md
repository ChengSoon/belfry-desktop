# Belfry 会话协作

Belfry 是一个终端工作台，它把每条 Agent 会话都摆在用户眼前。`belfry` 命令让这些会话互相
说话——派出去的活会注入对方终端，用户在协作面板里看得到每一条的去向和状态，也随时能切进
那条会话自己接手。

动手之前先确认自己就在这样一条会话里：

```bash
test -n "${BELFRY_TAB_ID:-}"
```

不成立就说明这里不是 Belfry 开的 Agent 会话，`belfry` 不可用——直接告诉用户，别去猜端点。

## 先看有谁

```bash
belfry peers
```

输出每条会话的**名字**、Agent 类型、忙闲和标题，自己那条前面带 `*`：

```
* planner   claude   （我自己）        — 把协作切回点对点
  reviewer  codex    idle · 可以派活   — 审一下队列回滚
  (未命名)  claude   要派活得先在侧栏给它起个名字 — 改 registry 的寻址
```

**名字是唯一的寻址键。** 标题不是——它由用户最后一条输入自动生成，每敲一条 prompt 就变。
没有名字的会话寻址不到；如果用户想派活给它，让他在侧栏双击那条会话起个名字。
名字可以是中文（`审查`、`前端`），字母开头、不带空格即可——汉字不是 shell 元字符，裸写就能派活。

## 派活

```bash
belfry send reviewer 审一下 src/auth.ts 的边界情况，只报可执行的问题
```

指令不用加引号，多个词会拼回去。要点：

- 同项目派活直接放行，返回「已送给…」表示已经交给投递队列。但**「已送出」不等于对方开工了**：
  对方正忙或卡在权限框时，指令会排在队里等它空闲。别在这之后假设它已经看到了。
- 在别人派给你的任务中间再派活，带上 `--parent <任务号>`——转包层数和成环检测靠它算准。
- 拒绝是有理由的：跨项目、给自己派、转包超过 3 手、绕成环、目标已退出都会当场说明原因。

## 收活与交差

```bash
belfry inbox                    # 派给我、还没结的
belfry done <任务号> 改完了，测试也过了
belfry fail <任务号> 这条要前端上下文，我这边看不到
```

收到的任务长这样，最后一行就是交差要敲的命令，照抄即可：

```
[belfry] 来自「planner」的任务 01m1bqyc
审一下 src/auth.ts 的边界情况
完成后执行：belfry done 01m1bqyc
```

**`done` 是唯一可信的完成信号。** Belfry 判断「你在忙还是空着」靠扫屏幕文本，那是猜的；
做完了不敲 `done`，派活方会一直看到「已送出 · 完成情况未知」。做不了就 `fail` 并说清原因，
那句话是对方唯一能看到的解释。

## 等对方交差再往下走

要串起「A 做完再交给 B」这种流程，派完之后盯着那条任务：

```bash
belfry send ui 按需求文档出一版原型   # 返回里带任务号
belfry wait <任务号>                 # 一直等到它交差
```

`wait` 只在对方敲了 `done` / `fail` 之后才返回，所以它返回就意味着那一步真的结束了，
可以接着派下一个人。要点：

- **默认一直等**，不设上限——有些活要跑很久，而给个上限只会让你在超时那一刻误判成
  「可以往下走了」。真需要上限时用 `--timeout <秒>`。
- **一直等不会挂死**：对方会话被关掉、用户在协作面板按「全部停下」、或者用户 Esc 掉你
  这条会话，三条路都会让 `wait` 返回。目标消失时它报的是「已作废」，那不是完成。
- **等之前先说一句你在等谁**。等待期间用户只看到你在「Working」，不知道卡在哪一步——
  开等之前留一句「已派给 ui，等它交差」，他才看得懂这段沉默。
- **超时不是完成**。给了 `--timeout` 而超时了，消息里会带上当前状态（排队中／已送出但
  还没交差），那都不是往下走的信号。
- 等多条就依次 `wait`：它们并行在跑，先等哪个都一样，总耗时等于最慢那个。
- 只能等自己派出去的任务；别人派的连状态都查不到。

## 命令面以 `--help` 为准

```bash
belfry --help
```

这份文档会过期，装在机器上的那个二进制不会。参数对不上时先查 `--help`，别猜。
失败信息走 stderr、退出码非零，里面通常已经写了下一步该敲什么。

## 这不是子代理

派活的对象是**用户已经开好、正摆在他眼前的一条会话**，不是你新起的一个子代理。区别决定了
什么时候该用哪个：

| | `belfry send` | 子代理（`spawn_agent` / Task） |
|---|---|---|
| 对方是谁 | 用户开的长期会话，有自己的历史和上下文 | 你临时起的，干完就没了 |
| 谁看得见 | 用户看得见整个过程，能随时接手 | 基本是黑盒 |
| 代价 | 占用用户的一个工作现场，会打断他在那边的思路 | 只花 token |
| 适合 | 需要另一个视角、另一个模型，或对方已经在那个上下文里 | 并行跑一批边界清晰的机械活 |

「这件事并行做会更快」是用子代理的理由，**不是**派活给别人会话的理由。

但反过来也要认得出信号：**用户已经在侧栏开好并命名了几条会话**（`项目经理`、`前端`、`测试`），
那就是他搭好了一个班子，说「交给前端」指的就是那条会话。这时候起子代理自己扮演前端，等于
把他摆好的人全都绕开了——而他开那些会话是为了能一个个看着、随时接手。拿不准就先
`belfry peers` 看一眼：**名单里正好有他点名的那个名字，就是它**。

worktree 并行又是第三件事——那是分支隔离，和这里无关。

## 分寸

- 派活前先 `peers`：确认对方在、闲着、而且名字没记错。
- 不要替用户回答别人终端里的权限确认框——那是他的决定。
- 你只能派活和交差；开会话、关会话、给会话起名都由用户在界面上做。
